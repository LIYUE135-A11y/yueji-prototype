# 美丽修行 · 工程目录与系统说明

> 给后续开发 / AI 代理快速建立上下文，避免漏改一端或漏同步。  
> 产品对外名称：**美丽修行**（界面里可见「阅己」店铺/品牌文案，属演示数据，勿与工程名混淆）。

---

## 1. 系统是什么

美妆内容 + 电商的 **H5 / uni-app 原型**：

| 端 | 目录 | 角色 |
|----|------|------|
| C 端 App | `美丽修行app/` | 用户浏览、下单、圈子/种草、我的订单等 |
| B 端运营 | `运营管理系统/` | 商品/订单/评价/装修/设置等后台 |
| 共享层 | `common/` | App ↔ 运营共用的 store / sync（`localStorage`） |
| 可选后端 | `server/` | Node + MySQL，持久化 `app_store` |

日常演示优先改两端的 **`preview.html`**（大单页）；uni-app 的 `pages/`、`admin/` 为同源能力的另一套入口。

## 3. 改哪里（防漏）

| 场景 | 优先改 |
|------|--------|
| H5 演示（订单弹窗、我的订单 UI） | `运营管理系统/preview.html`、`美丽修行app/preview.html` |
| 双端数据同步 | `common/*-store.js`、`common/profile-*-sync.js` |
| uni 真页面 | 对应 `pages/**` + App `common/*-data.js` |
| 运营 Vue 页 | `运营管理系统/admin/**`（及 `src/admin/**` 若存在双份） |
| 库表 / HTTP | `server/` + `common/db-bridge.js` |

原则：**功能若涉及 C/B 两端，先想清楚 store key，再改 UI；只改一边必漏。**

## 4. 已打通模块备忘

- **商品 / 活动券 / 购物车 / 订单 / 评价 / 售后**
- **商品评价**：运营「评价管理-商品评价」由「商品管理」`PRODUCT_LIST` 按品类自动生成多样评价（星级/图文/审核态/回复），经 `ReviewStore.syncProductReviewsWithCatalog`；订单回写评价保留
- **装修入口**（`decor-entry-store`）+ **自定义页面**（`zhuangyan_decor_pages_v1`，见 `docs/PRD-自定义页面.md`）
- **社区内容**：圈子、种草、话题、文章、动态 feed
- **订单 → 种草**：App「我的订单」已评价旁「去种草」→ 发布弹窗 → `GrassStore`（`yueji_grass_list_v2`）→ 运营「种草管理」；本人主页 Tab「我在种草」展示；订单可标记 `grassPublished` / `grassId`
- **订单查看弹窗**（运营 `preview.html` → `buildOrderDetailHtml`）：六块——基本信息 / 发票信息 / 买家信息 / 商品信息 / 费用信息 / 操作信息  
  - 货号 = **订单号**；多商品按**整单汇总**；缺费用字段用 `0.00` 或由原价−实付推导  
  - 列表：「查看」常显；「发货」仅待发货

### 订单状态文案（App ↔ 运营应对齐）

待付款 / 已付款 / 待发货 / 确认收货（或待收货）/ 已完成  

活动/促销名称**不要**当成商品标题；商品名走商品目录，活动名可作优惠券标签。

## 6. 新模块检查清单

创建或大改一个模块前过一遍：

1. 运营端：列表 + 详情/弹窗要不要做？  
2. App 端：入口与展示在哪？  
3. `common`：是否新 store + 新 `localStorage` key？是否加入 `db-bridge`？  
4. 是否需要 App ↔ 运营回写（类似 `profile-order-sync`）？  
5. 只改 `preview.html`，还是 `pages/` / `admin/` 一起改？  
6. 原型无真实后端：缺字段用 `-` / `0.00` / 合理推导，不阻塞演示。

## 7. 约定

- 产品文案用中文；状态文案与运营列表对齐。  
- 大文件（尤其两个 `preview.html`）**局部改**，勿整文件重写。  
- 演示优先、字段可占位；勿为「完整后端」阻塞原型。  
- 提交代码前确认：改了 UI 是否也改了 sync；改了 store 是否两端都读到。
